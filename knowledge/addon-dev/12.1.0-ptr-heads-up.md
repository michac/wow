## The dominant theme: auras go fully secret (HIGH)

At 12.1.0 aura secrecy escalates from *per-instance* to *wholesale*. This is the
single biggest change and it touches three files plus one of our own projects.

- `C_UnitAuras.GetUnitAuras` / `GetUnitAuraInstanceIDs` return **secret vectors**;
  `AuraData` structs are **always fully secret**. ⚠ **"Per-spell/-ID lookups still
  work" is TOO STRONG — corrected 2026-08-05.** Those three getters
  (`GetPlayerAuraBySpellID`, `GetUnitAuraBySpellID`, `GetAuraDataBySpellName`)
  carry the **`RequiresNonSecretAura` Precondition** already at 12.0.7
  (`UnitAuraDocumentation.lua:208, 335, 372`; predicate at `:560`), i.e. they answer
  only for auras on a **per-spell non-secret allowlist**. Being a precondition,
  a secret-flagged spell yields **silent absence** — not an error, not a secret.
  And the allowlist is **shrinking build-over-build**: Ebon Might (395296) was
  reportedly removed from it in build 68824, which killed a shipping addon's
  numeric `expirationTime` path and forced a rewrite onto the aura-container engine.
  So the survival story is conditional and *moving*, not a stable fallback.
  [Tier 1 for the precondition; Tier 3 for the narrowing datapoint.]
- The **`UNIT_AURA`** event delivers a **fully secret payload** while auras are
  secret.
- `UnitIsCharmed` / `UnitIsPossessed` become secret **when auras are secret**
  (couples them to this change).
- **Sanctioned replacement:** new managed widget types
  **`AuraContainer` / `AuraButton` / `ManagedAuraContainer`** +
  `Enum.ForbiddenAspect` — the "display auras without seeing them" path.
  **`SecureAuraHeaderTemplate` is removed** in favor of them. ⚠ That removal is
  **not corroborated by our 2026-08-05 mining run** — the mined addon never used
  the template on either branch, so we have no evidence either way; it still exists
  at 12.0.7 (`Blizzard_RestrictedAddOnEnvironment/SecureGroupHeaders.lua/.xml`).

  **THE REPLACEMENT CONTRACT, as observed in a shipping mid-migration addon**
  (EllesmereUI 8.7.5, all `IS_121`-gated; read for API discovery only, no code
  copied). ⚠⚠ **Tier 3 against a moving target — read every name as *"real at some
  PTR build"*, never as a shipping signature.** That addon's own history shows the
  API changing twice underneath it: a `SetAuraLayout*` → `SetFlowLayout*` rename and
  an `Enum.CustomAuraButtonBorderStyle` → `…DispelTypeTextureStyle` deletion, both
  mid-port. Re-verify everything on PTR before authoring a single edit.

  - **Construction is a fixed order, and `SetUnit` comes LAST:**
    `CreateFrame("AuraContainer", nil, parent, "CustomAuraContainerTemplate")` → set
    layout → `AddAuraGroup` / `AddAuraSlot` → `SetUnit(unit)` → `UpdateAllAuras()`.
    Assigning the unit re-evaluates event registrations, and those are gated on the
    container already having content — set it first and `UNIT_AURA` never registers.
    The container must also be **visible with a real rect**, or the engine builds it
    and then parses nothing, silently.
  - ⚠⚠ **A button never learns which aura it shows, and that is the design.** You
    declare intent (a filter string + `candidateFilters`) and register **output
    sinks** — `SetIcon`, `SetDurationCooldown`, `SetApplicationCount`,
    `SetDurationText` — which the engine fills. This is §4.8's secret→visual-sink
    thesis promoted to a first-class widget API, and it is the answer to "how do I
    still show auras".
  - ⚠⚠ **`initializeFrame` is the ONLY window in which addon code may touch a
    button.** The engine applies an access restriction the moment your callback
    returns, blocking **reads and writes** thereafter while auras are secret.
    *Build everything at creation, then never touch it.* Any design that plans to
    re-read a button later is wrong from the start. (Regions the addon created
    itself stay writable.)
  - ⚠ **Forbidden aspects are conferred at CREATION only.** Reparenting into an
    aspect-bearing subtree does **not** grant them — a field attempt hard-errored.
    Birth the object inside a `DisableUntrustedLayoutScriptsTemplate` holder instead.
    Separately, *registering events* stamps a frame with `EventRegistrations`, and
    the restricted environment refuses aspect-bearing frames — so event listeners
    must live on plain sidecar frames. **This is the mechanism behind the
    `Enum.ForbiddenAspect` bullet below**, which today reads as mere granularity.
  - ⚠ **The flow layout only ANCHORS** (`SetFlowLayout*`, axis from
    `AnchorUtil.FlowLayoutAxis`) — button *size* is the addon's job, and an unsized
    button renders nothing.
  - Filter strings gain a **`!` negation** prefix (verified absent at 12.0.7:
    `Blizzard_FrameXMLUtil/AuraUtil.lua:157-176`), and **groups cannot OR** — a
    union display must be decomposed into one group per class made mutually
    exclusive by negation. Group filter strings are **fixed at declaration**.
  - The `UNIT_AURA` payload **table itself** can be a secret value, independently of
    its fields: `issecretvalue(updateInfo)` **before indexing**, then again on
    `isFullUpdate`. `if updateInfo.isFullUpdate then` is a hard error.

  Everything above, plus the "what may stop working" exposure table, is tracked in
  [`mined-pending-verification.md`](./mined-pending-verification.md) §C.

## Unit-identity APIs return secrets (HIGH) — `security-taint-and-restricted-data.md`

The `SecretWhenUnitIdentityRestricted` set (§4.7, ~15 applications today) widens
sharply. Newly identity-secret when the unit's identity is secret:

`UnitClass`, `UnitClassBase`, `UnitSex`, `UnitSexBase`, `UnitRace`,
`UnitPhaseReason`, `UnitGroupRolesAssigned`, `UnitGroupRolesAssignedEnum`,
`UnitIsOwnerOrControllerOfUnit`, `UnitIsRaidOfficer`, `UnitInRaid`, `UnitIsPVP`,
`UnitIsGroupLeader`, `UnitIsGroupAssistant`, `UnitLeadsAnyGroup`,
`UnitGetAvailableRoles`, `GetInspectSpecialization`.

- **The one near-contradiction / relaxation:** `UnitName` **no longer returns
  secrets during active PvP matches** — softens the current "identity-restricted
  broadly" framing (§4.7 lines ~1050–1051 use `UnitName` as the worked example).
- `GetGuildInfo` **no longer accepts compound unit tokens** (signature change).
- Impact for authors: class/role/race are read by unit-frame and raid tools in
  combat — real breakage vector. Mechanism is unchanged (only the covered set
  grows), so an **inline heads-up** at §4.7/§4.10 suffices.

## XML schema additions (MEDIUM–HIGH) — `module-architecture.md` + `anatomy-and-runtime.md`

The XML-composition material is a core strength of `module-architecture.md`, so
these extend it directly:

- **New `<Mixins>` XML element** (supports `source="local"`, allows nested table
  refs in mixin keys) — joins the existing `mixin=` **attribute** documented at
  `module` §3.1 (lines ~398–416) + rule 25 (~1250–1255). `source="local"` is a
  new way to reach a **private addon table** from XML.
- **`<KeyValue source="local">`** — not currently documented (`<KeyValue>` absent
  from both files); pairs conceptually with `<Mixins> source="local"`.
- **New per-file `[Bootstrap]` directive** for Load-on-Demand addons: listed
  files load on startup even for LoD addons (addon must be enabled). This is an
  **exception to an absolute** — qualify `anatomy` rule 20 (lines ~1168–1184) +
  §4.3 (~494–540), `module` §5.4 (~935–948) + rule 24, and the per-line
  conditional table `anatomy` §2.4 (~278–306).

## New object types / texture APIs (MEDIUM) — `frames-textures-animation.md`

Nothing contradicted — all additive; the type censuses (§1.1/§1.3) become
incomplete.

- **`VectorGraphics`** — new SVG-rendering UI object type. Note it **lacks**
  rotation / masking / tex-coords (currently) — worth flagging against exactly
  the TextureBase channel-2 surface in §5.2 (lines ~682–715) and masks §5.7
  (~872–884), where a reader would expect those methods.
- **Radial progress textures:** `SetRadialProgressBarPercent`,
  `SetRadialProgressBarStartOffset`, `SetRadialProgressBarEndOffset`,
  `SetRadialProgressBarReverse`, `SetRadialProgressBarFeather` — new
  texture-geometry channel, siblings of §5.2's tex-coord/slice cluster. This is
  the classic Cooldown-Manager radial-fill surface (see project note below).
- **`Frame:SetOnUpdateMode(mode)`** — modes `Disabled` / `RunWhenVisible`
  (default) / `RunWhenVisibleOnce` / `RunOnce` / `RunAlways`. A native alternative
  to the manual dirty-flag-then-clear run-once pattern in `module` rule 21 / §4.3
  (lines ~696–706). Also new frame methods `ResizeToBoundsRect` (extends `frames`
  §3 sizing) and `IsRolesetFiltered`.
- **`AnchorUtil.CreateFlowLayout`** — new sibling to the layout-factory list
  already enumerated verbatim at `frames` §3.5 (lines ~471–474). Cleanest,
  lowest-risk future inline add.

## Discovery, CVars, ecosystem (LOW–MEDIUM)

- **New CVar `tooltipShowAuraSpellIDs`** (default `0`, **does not persist between
  sessions**) surfaces aura spell IDs in tooltips — a discovery aid worth adding
  to `api-events` §5.1 (line ~862) next to `/api` and `/eventtrace`, especially
  since aura reads get harder. (`state-persistence` note: same session-only
  category as its existing `addonChatRestrictionsForced` remark.)
- **`autoLootDefault` now account-wide** (was character-specific); **`C_CVar.AreCVarsLoaded`**
  added (a load-lifecycle probe, parallel to `state-persistence` §1.3's
  `ADDON_LOADED`-gates-SV-reads model). Neither contradicts existing text — CVars
  aren't currently treated as a persistence store.
- **Ecosystem exposure (`libraries-and-ecosystem.md`):** **oUF** and **ElvUI**
  are built on aura headers / secure unit templates and are mid-migration to
  AuraContainers. Caveat their "Active" rating (line ~678) and the §11 "read as
  living documentation" recommendation. Note: `oUF.toc` **already declares
  `## Interface: 120007, 120100`**. Serializers (AceSerializer / LibSerialize /
  LibDeflate, §5.2 ~461–471, §10 ~743–745) and SavedVariables (§3 ~337–368) gain
  auras as a large new secret-value hazard source — reinforces, doesn't
  contradict.

## Private Script Objects (MEDIUM) — `security-taint-and-restricted-data.md`

New mechanism splitting a Lua object across partitions; a **Forbidden Partition**
is inaccessible to addons. New methods `FrameScriptObject:HasAccessConstraints`
and `FrameScriptObject:CanBeAccessedInContext` (the latter replaces removed global
`CanAccessObject`). Entirely new; nearest neighbours are the value/table-access
primitives §4.4 (`canaccessvalue`/`canaccesstable`/`canaccesssecrets`, ~802–805).
Additive — no existing sentence needs correction.
